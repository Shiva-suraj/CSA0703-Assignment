## Q1 – Which Socket Receives the Segment? (7 Marks)

### 1. TCP demultiplexing

An established TCP connection is identified by a four-part tuple: source IP address, source port, destination IP address and destination port. A server can listen on one TCP port and still handle many clients because each established connection has a different tuple. A new TCP SYN is first handled by the listening socket; after the handshake, the operating system associates the connection with a separate connected socket.

| Incoming segment | Correct destination |
|---|---|
| TCP 49.205.3.9:40001 → 198.51.100.10:8443 | Established socket for that client tuple |
| TCP 106.200.7.4:40000 → 198.51.100.10:8443 | A different established socket; source IP differs |
| TCP SYN 157.48.9.1:52100 → 198.51.100.10:8443 | Listening socket; creates a new connection after handshake |
| UDP 49.205.3.9:40000 → 198.51.100.10:5060 | UDP socket bound to local port 5060 |
| TCP segment with no matching connection and no SYN | No established socket matches; normally discarded or reset according to TCP state |

Two clients may use the same source port because their source IP addresses differ. UDP commonly delivers datagrams to a socket bound to a local port; the application can inspect each datagram's sender address and port.

### 2. Header overhead

For IPv4 without options, the IP header is 20 bytes. UDP adds 8 bytes and a normal TCP header adds 20 bytes. For an 80-byte application payload:

- UDP: 20 + 8 = 28 header bytes; total = 108 bytes; overhead relative to payload = 28/80 × 100 = **35%**.
- TCP: 20 + 20 = 40 header bytes; total = 120 bytes; overhead relative to payload = 40/80 × 100 = **50%**.

These figures exclude Ethernet/Wi-Fi, TLS and other encapsulation. TCP's extra fields support sequence numbers, acknowledgements, flags and flow control.

### 3. Transport choice

| Function | Recommended protocol | Reason |
|---|---|---|
| Login and payment | TCP with TLS / HTTPS | Reliable, ordered and encrypted transaction delivery |
| Live proctoring video | WebRTC media over UDP with SRTP | Low delay; stale frames are less useful than fresh frames |
| Invigilator chat | Reliable data channel or TCP-based WebSocket | Messages should arrive completely and in order |
| Answer-sheet upload | HTTPS over TCP or QUIC | Complete delivery, retry and application-level confirmation |

UDP is not automatically reliable or secure. If an application uses UDP directly, it must implement any required loss recovery, ordering, congestion control and security. Real-time video can tolerate some loss, while payment and answer submission cannot.

### 4. Persistent connection calculation

For 60 answers of 200 bytes each, using one persistent TCP connection requires one TCP three-way handshake. If each answer opens a new sequential connection, there are 60 handshakes. At 50 ms RTT, the additional setup delay is (60 − 1) × 50 ms = **2.95 seconds**. The 59 extra handshakes add 177 handshake segments (three per handshake), excluding data and close packets. Persistent connections reduce setup delay and packet overhead.

### 5. TCP message framing code

TCP is a byte stream; one send call does not necessarily correspond to one receive call. A length prefix makes message boundaries explicit.

```python
import struct

def send_msg(sock, text):
    data = text.encode("utf-8")
    sock.sendall(struct.pack("!I", len(data)) + data)

def recv_exact(sock, n):
    data = b""
    while len(data) < n:
        chunk = sock.recv(n - len(data))
        if chunk == b"":
            raise ConnectionError("connection closed")
        data += chunk
    return data

def recv_msg(sock):
    length = struct.unpack("!I", recv_exact(sock, 4))[0]
    return recv_exact(sock, length).decode("utf-8")
```

3. Run a UDP client/server and inspect source port, destination port, length and checksum.
4. Use `ss -tunap` to view listening and established sockets.
5. If using Linux `tc netem`, apply controlled loss and record delivery and retransmissions.

**Conclusion:** TCP identifies established connections using the connection tuple. UDP normally uses the local bound port and sender information. Persistent TCP connections are efficient for many related messages.

## Q2 – Why Did the Download Slow Down? (7 Marks)

### 1. Congestion-window interpretation

The congestion window (cwnd) limits the amount of unacknowledged data in flight. Slow start grows the window approximately exponentially. Congestion avoidance grows it approximately linearly. A detected loss causes a reduction.

| Event | Observed change | Interpretation |
|---|---|---|
| Start | 1, 2, 4, 8, 16, 32 | Exponential slow start; threshold near 32 segments |
| RTT 9 to 10 | 35 to 17 | Approximately halves; consistent with fast retransmit/recovery |
| RTT 13 to 14 | 20 to 1 | Reset to one segment; consistent with retransmission timeout |

The trace is compatible with Reno-style fast recovery after the first event and a later timeout. A graph alone cannot prove the exact mechanism; packet-level ACK and retransmission evidence is required.

### 2. Throughput at RTT 7

Given cwnd = 33 segments, MSS = 1,460 bytes and RTT = 80 ms = 0.08 s:

`Throughput ≈ cwnd × MSS × 8 / RTT`

`= 33 × 1,460 × 8 / 0.08 = 4,818,000 bit/s ≈ 4.82 Mbps.`

This is an estimate. Real throughput may be lower due to headers, ACK traffic, receiver window, bottleneck capacity and competing flows.

### 3. AIMD fairness

Additive Increase Multiplicative Decrease (AIMD) gradually increases each flow's window when the network is uncongested and proportionally reduces windows when congestion occurs. Repeated additive increases and multiplicative decreases tend to move competing flows toward a fairer share of a bottleneck.

```python
def run(x1, x2, capacity, rounds):
    history = [(x1, x2)]
    for _ in range(rounds):
        if x1 + x2 > capacity:
            x1 /= 2
            x2 /= 2
        else:
            x1 += 1
            x2 += 1
        history.append((x1, x2))
    return history
```

This is a simplified illustration, not a complete TCP implementation.

### 4. Congestion-control comparison

| Algorithm | Response | Strength / limitation |
|---|---|---|
| Tahoe | Resets cwnd to one MSS after loss | Conservative; slower recovery |
| Reno | Fast retransmit/recovery halves cwnd for duplicate ACK loss; timeout restarts slow start | Faster for isolated loss; multiple losses can be difficult |
| CUBIC | Uses cubic window growth around previous congestion point | Designed for high-bandwidth paths |
| BBR | Estimates bottleneck bandwidth and propagation RTT | Useful candidate for high-delay paths; test against competing flows |

For a 150 ms long-distance path with random loss, test CUBIC and BBR against Reno using iperf3. Compare throughput, retransmissions, RTT and fairness instead of assuming one algorithm always wins.

### 5. ECN

Explicit Congestion Notification allows a router to mark packets rather than drop them when congestion is developing. The receiver echoes the indication and the sender reduces its window. ECN can avoid some retransmissions, but it cannot prevent loss from link errors, route failures or queues that overflow.

**Practical tests:** Plot Tahoe/Reno cwnd against RTT; run two simultaneous iperf3 flows; inspect `ss -ti`; apply controlled delay/loss using `tc netem`.

**Conclusion:** The RTT-7 estimate is about 4.82 Mbps. The later cwnd reset suggests a timeout. Long-distance performance should be measured using suitable congestion-control algorithms.

## Q3 – Why Does the Product Page Take 10 Seconds? (7 Marks)

### 1. Page-load calculations

There is one HTML file and 60 small objects. RTT = 80 ms. Assume negligible transmission and server processing time, no DNS/TLS setup, and that object URLs are discovered after the HTML arrives.

| Method | Approximate RTT count | Estimated time |
|---|---:|---:|
| Non-persistent, sequential | 2 × 61 = 122 | 122 × 80 ms = **9.76 s** |
| Persistent HTTP/1.1, no pipelining | 1 setup + 1 HTML + 60 objects = 62 | **4.96 s** |
| Persistent with pipelining | 1 setup + 1 HTML + 1 object batch = 3 | **0.24 s** |
| Six parallel non-persistent connections | 2 HTML RTT + 10 waves × 2 RTT = 22 | **1.76 s** |

The six-connection estimate assumes ten waves of six objects. Browser connection limits, caching, TLS and server processing can change actual timings.

### 2. HTTP/2 and HTTP/3

HTTP/2 multiplexes multiple streams over one TCP connection. It reduces application-level blocking, but TCP delivers one ordered byte stream; loss of one TCP segment can temporarily block delivery of later bytes for all streams.

HTTP/3 uses QUIC over UDP. QUIC provides reliable streams and congestion control. Loss in one stream does not necessarily block delivery on independent streams. Congestion can still affect the connection as a whole.

### 3. Caching

- `Cache-Control: max-age` tells a browser how long it can reuse a response.
- Versioned static assets can use a long lifetime and `immutable`.
- `ETag` validates whether a cached object changed.
- `If-None-Match` allows a conditional request; unchanged content can return `304 Not Modified`.

A second visit can avoid downloading many objects, depending on their cache policy and whether they changed.

### 4. Edge-server calculation

At an edge server with 15 ms RTT:

| Method | RTT count | Estimated time |
|---|---:|---:|
| Non-persistent sequential | 122 | 1.83 s |
| Persistent, no pipeline | 62 | 0.93 s |
| Persistent with pipelining | 3 | 0.045 s |
| Six parallel non-persistent | 22 | 0.33 s |

For non-persistent sequential loading, the estimated improvement is 9.76 − 1.83 = **7.93 seconds**.

**Practical tests:** Use the browser Network panel to record protocol, connection count, bytes and load time. Compare first visit and cached second visit, and test with added delay.

**Conclusion:** Persistent connections, multiplexing, caching and edge delivery reduce page-load time. HTTP/3 avoids TCP's cross-stream head-of-line blocking.

## Q4 – How Many Queries Reach the Shop’s DNS Server? (7 Marks)

### 1. Resolver cache calculation

One resolver is asked for a name every five seconds for one hour: 720 client requests. Under the simplified model, an authoritative query is sent when the cached answer expires.

| TTL | Queries per resolver per hour | 400 resolvers |
|---|---:|---:|
| 20 s | 3,600 / 20 = 180 | 72,000 |
| 60 s | 3,600 / 60 = 60 | 24,000 |
| 300 s | 3,600 / 300 = 12 | 4,800 |
| 3,600 s | 1 | 400 |

The authoritative server generally sees cache misses from recursive resolvers, not every phone request. Short TTL increases refresh frequency; long TTL reduces load but delays address changes.

### 2. Recursive and iterative DNS

A phone normally sends a recursive query to its configured resolver. If the answer is not cached, the resolver performs iterative queries: root server, relevant TLD server, then the authoritative server. The resolver returns the final answer and caches it according to TTL.

### 3. DNS record types

| Record | Purpose |
|---|---|
| A | Hostname to IPv4 address |
| AAAA | Hostname to IPv6 address |
| CNAME | Alias to canonical name |
| MX | Mail exchanger |
| NS | Authoritative name server |
| TXT | Text data for verification and policy records |

DNS commonly uses UDP port 53 for small queries and answers. TCP is used for zone transfers and cases requiring stream transport. Encrypted options include DoT and DoH.

### 4. Cache implementation

```python
def get(self, name, now):
    item = self.store.get(name)
    if item is None:
        return None
    address, expiry = item
    if now < expiry:
        return address
    del self.store[name]
    return None
```

With TTL 3,600 seconds, the first request causes an upstream query; later requests in the hour are cache hits. If the shop changes its IP before expiry, some resolvers may continue returning the old address until the cached entry expires.

### 5. Round-robin and DoH

Round-robin DNS returns different addresses across responses, but caches and existing connections mean it is not a perfect load balancer. A shorter TTL improves update speed but increases authoritative query load.

For a 30 ms RTT, a cold DoH connection may need approximately TCP setup (1 RTT), TLS 1.3 setup (1 RTT) and DNS request/response (1 RTT): about **90 ms**. A warm connection needs roughly one RTT, about **30 ms**. Plain UDP DNS also commonly needs one request/response RTT. DoH encrypts traffic between client and resolver but does not hide the query from that resolver.

**Conclusion:** A 60-second TTL produces about 24,000 authoritative queries per hour across 400 continuously active resolvers under this model.

## Q5 – How Many Trunk Lines Does the Help Desk Need? (6 Marks)

### 1. Offered traffic and Erlang B

Arrival rate = 120 calls/hour. Average holding time = 3 minutes.

`A = 120 × 3/60 = 6 Erlangs.`

Erlang B estimates blocking probability when all trunk lines are busy, assuming random arrivals, independent call durations and no waiting queue.

```python
def erlang_b(traffic, lines):
    b = 1.0
    for n in range(1, lines + 1):
        b = traffic * b / (n + traffic * b)
    return b
```

| Lines | Blocking probability (approx.) | Assessment |
|---:|---:|---|
| 6 | 26.49% | Too high |
| 8 | 12.19% | Too high |
| 10 | 4.31% | Too high |
| 12 | 1.14% | Slightly above 1% |
| 13 | About 0.5% | Meets 1% target |

Therefore, **13 lines** are needed for blocking probability at or below 1%. If calls increase by 50%, arrival rate becomes 180/hour and offered traffic becomes 9 Erlangs; recalculate the trunk count for the same blocking target.

### 2. M/M/1 comparison

For arrival rate λ = 80 packets/s and service rate μ = 100 packets/s:

- Utilisation: ρ = λ/μ = 0.8.
- Average time in system: W = 1/(μ − λ) = 1/20 = **0.05 s = 50 ms**.

For two independent 50-packet/s queues with an even split, each receives 40 packets/s. Each queue has W = 1/(50 − 40) = **0.1 s = 100 ms**. This is not equivalent to a pooled two-server queue; a pooled M/M/2 system requires a different calculation.

### 3. Token bucket

Bucket capacity = 500 KB = 4,000,000 bits. Refill rate = 1 Mbps. Backup sends at 8 Mbps. Net token drain = 7 Mbps.

Burst duration = 4,000,000 / 7,000,000 = **0.571 s**. Total transmitted during burst = 8 Mbps × 0.571 s ≈ 4,571,429 bits ≈ **571 KB**. After the bucket empties, long-term average is limited to 1 Mbps.

### 4. DiffServ recommendations

| Traffic | Suggested class | Reason |
|---|---|---|
| Voice | EF | Low delay and jitter; use admission control and policing |
| Video lecture | Suitable AF class | Assured throughput and controlled loss |
| Booking database | AF | Reasonable response time |
| Nightly backup | Best effort or shaped AF | Background traffic should not overwhelm interactive work |
| E-mail | Best effort | Delay tolerant |

Do not mark unlimited traffic as EF; an overloaded priority queue can become congested. Erlang C can model a waiting queue, while Erlang B models blocked calls.

**Conclusion:** The offered load is 6 Erlangs. Thirteen trunks meet the 1% blocking target under the stated assumptions. Queueing and QoS should be selected based on measured traffic.

## Q6 – How Soon Does the First Video Byte Arrive? (6 Marks)

### 1. First-byte timing

RTT = 120 ms. Assume a new connection, no loss, negligible server processing and one request/response RTT after security setup.

| Protocol | Approximate RTT sequence | First response byte |
|---|---|---:|
| TCP + TLS 1.2 | TCP 1 + TLS 2 + request 1 | 4 RTT = **480 ms** |
| TCP + TLS 1.3 | TCP 1 + TLS 1 + request 1 | 3 RTT = **360 ms** |
| QUIC first visit | QUIC handshake 1 + request 1 | 2 RTT = **240 ms** |
| QUIC 0-RTT resumption | Early request and response | About 1 RTT = **120 ms** |

These are simplified estimates. Early data acceptance, DNS, radio scheduling and processing affect real timings.

### 2. 0-RTT replay risk

TLS 1.3 0-RTT data can be replayed because it is sent before a fresh handshake is fully complete. Avoid non-idempotent operations such as purchases, payments, final answer submission or account changes in early data. Read-only operations may be suitable if replay has no harmful effect. A server can reject early data and require a retry after handshake completion.

### 3. TLS 1.3 and forward secrecy

TLS 1.3 removes obsolete cryptographic options and provides a streamlined handshake. Ephemeral key exchange can provide forward secrecy: later theft of the server's long-term private key should not reveal old session keys derived from temporary secrets that have been discarded.

### 4. QUIC and UDP fallback

QUIC uses UDP so transport functions can evolve in user space. It provides encryption, stream multiplexing, loss recovery and congestion control. Some firewalls block or limit UDP port 443. Applications should attempt HTTP/3 and fall back to HTTP/2 over TLS/TCP when necessary.

### 5. Four-stream loss comparison

With four video streams over one TCP connection, loss of a TCP segment can block later bytes across all streams until retransmission fills the gap. QUIC's independent streams avoid this transport-level cross-stream blocking. Congestion control is still shared, so a loss event can reduce the rate for the connection.

At 100 packets/s and 2% independent loss, expected losses in 10 seconds = 100 × 10 × 0.02 = **20 packets**. This does not imply 20 application stalls; retransmission and loss-recovery behaviour determine user-visible impact.

**Practical tests:** Capture TLS 1.3 in Wireshark; use `openssl s_client -connect hostname:443 -tls1_3`; inspect browser Network panel for h3; compare timings with added delay.

**Conclusion:** HTTP/3 is a strong choice for mobile lecture delivery, with HTTP/2 fallback. Do not use 0-RTT for state-changing examination actions.

Window-limited throughput:

`65,536 × 8 / 0.35 = 1,498,000 bit/s ≈ 1.50 Mbps.`

`1,460 / (0.35 × 0.2) = 20,857 bytes/s ≈ 166.9 kbps.`

This is an approximate simplified model, not an exact TCP prediction. It indicates that the loss estimate is more restrictive than the stated window limit. Resumable/chunked uploads, checksums, retries and durable receipts improve answer-sheet reliability.
